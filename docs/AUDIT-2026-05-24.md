# Audit: Modal, Data Pipeline, Codebase — 2026-05-24

Three-part audit covering Modal deployment readiness, the data pipeline's
quality controls, and broad codebase health. Findings are concrete and
reference `file:line` so they can be acted on directly.

Two improvements already landed alongside this report:

- `scripts/modal-deploy.sh` — idempotent bootstrap that validates secrets,
  creates/refreshes the `bfi-secrets` Modal Secret, and deploys both apps.
- `supabase/migrations/20260525_fees_verified_dedup.sql` — adds the missing
  Tier-2 dedup guard (see Pipeline §Risk 1). Aborts safely if existing

## Part 1 — Modal Setup

### State today

Two apps defined in `fee_crawler/`:

| App                              | File                              | Purpose                                  |
|----------------------------------|-----------------------------------|------------------------------------------|
| `bank-fee-index-workers`         | `fee_crawler/modal_app.py:75`     | All scheduled crons + ASGI/HTTP sidecars |
| `bank-fee-index-preflight`       | `fee_crawler/modal_preflight.py:35` | Pre-deploy readiness checks            |

**Five cron slots are fully consumed** (Modal Starter free-tier cap):

| Cron                     | Schedule (UTC) | Image           | Purpose                                                            |
|--------------------------|---------------:|-----------------|--------------------------------------------------------------------|
| `run_discovery`          | `0 2 * * *`    | browser         | Sweep institutions for missing fee-schedule URLs                   |
| `run_pdf_extraction`     | `0 3 * * *`    | pdf             | Extract fees from PDF schedules (fast path)                        |
| `run_browser_extraction` | `0 4 * * *`    | browser         | Extract from JS-rendered pages via Playwright                      |
| `run_post_processing`    | `* * * * *`    | pdf             | Per-minute dispatcher: agent ticks + 05:00 review + 06:00 publish  |
| `ingest_data`            | `0 10 * * *`   | pdf             | Daily FRED/NYFed/BLS/OFR + weekly + quarterly call-report ingestion |

The `run_post_processing` dispatcher is the architectural pivot (D-05, Phase
62b): one every-minute cron replaces 6+ dedicated crons using
`workers_last_run` idempotent gates. Single-purpose tasks
(`run_monthly_pulse`, `darwin_nightly_drain`) are manual-only because no
sixth slot is available.

### What's required to ship

The Modal `bfi-secrets` Secret must contain:

```
DATABASE_URL, R2_ENDPOINT, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY,
R2_BUCKET, ANTHROPIC_API_KEY, FRED_API_KEY, BFI_APP_URL,
REPORT_INTERNAL_SECRET, REPORT_CRON_SECRET
```

The new `scripts/modal-deploy.sh` reads these from `.env.local`, generates
the two `REPORT_*_SECRET` values if missing, and runs:

```bash
modal secret create bfi-secrets --force <kv-pairs>
modal deploy fee_crawler/modal_app.py
modal deploy fee_crawler/modal_preflight.py
```

Plus convenience flags:

```bash
bash scripts/modal-deploy.sh --preflight   # health check only
bash scripts/modal-deploy.sh --secrets     # rotate the Secret only
```

### Gaps worth knowing before first deploy

- **Cron slots are at cap.** Any new scheduled work must piggyback on
  `run_post_processing` with a `workers_last_run` time-gate. There is no
  room for naive `@app.function(schedule=...)` additions.
- **No retry on first DB connect** — workers assume Postgres reachable;
  first failure crashes the function (`modal_app.py:110`, `modal_app.py:128`).
- **Browser-image IPv6→Supabase issue** — `generate_report()` posts to
  `BFI_APP_URL/api/reports/[id]/assemble` instead of writing direct to DB
  precisely because Modal browser containers can't reach Supabase via IPv6
  (see comment at `modal_app.py:643-646`). Implication: report jobs fail
  silently if the Next.js app is down.
- **No preflight on a schedule** — `modal_preflight.py` only runs when
  invoked manually. Consider piggybacking it onto the per-minute dispatcher
  (e.g. once an hour).
- **Sidecar files not in tree yet** — `darwin_api()` and `magellan_api()`
  (`modal_app.py:820, 838`) import from `fee_crawler/darwin_api.py` and
  `fee_crawler/magellan_api.py`. Verify these exist before deploying or
  comment out the ASGI definitions.

## Part 2 — Data Pipeline & Quality

### Pipeline stages

```
seed (FDIC/NCUA)           → crawl_targets
discover (Playwright/BS4)  → crawl_targets.fee_schedule_url
crawl + extract (Haiku)    → fees_raw            ← Tier 1, append-only
verify (Darwin agent)      → fees_verified       ← Tier 2, canonical_fee_key mandatory
publish (handshake event)  → fees_published      ← Tier 3, INSERT-only
```

Confidence thresholds (from `fee_crawler/validation.py` + `config.yaml`):

| Threshold                          | Value | Used by                              |
|------------------------------------|------:|--------------------------------------|
| `confidence_auto_stage_threshold`  | 0.85  | `validation.py:187` — auto-stage gate |
| `confidence_approve_threshold`     | 0.90  | `auto_review.py:26,49` — auto-approve |
| `outlier_std_dev_threshold`        | 3.0   | `outlier_detection.py:17` — IQR multi-plier |

Audit trail is well-designed: `fee_reviews` records every status transition,
`fees_published_rollback_log` tracks every rollback batch, and content
fields on the three fee tables are immutable by convention (`outlier_flags`
is the only mutable column on `fees_raw` / `fees_verified`).

### Top 5 risks

1. **No UNIQUE constraint on `fees_verified`** (HIGH) — `supabase/migrations/20260420_fees_tier_tables.sql:48-83`. Two
   Darwin verifications of the same `fees_raw` row, or two extractions of
   the same fee, silently land as duplicate rows. **Fixed** by
   `supabase/migrations/20260525_fees_verified_dedup.sql` (this PR).
   Follow-up: Darwin promotion path must switch to
   `INSERT … ON CONFLICT (institution_id, canonical_fee_key, amount, frequency) DO UPDATE`
   to avoid raising the new unique-violation in steady state.

2. **`fees_raw.institution_id` is not a foreign key** (MED) —
   `supabase/migrations/20260420_fees_tier_tables.sql:13`. The comment
   says "denormalized; required where the data supports it." If
   `crawl_targets` is re-seeded after FDIC ID drift, raw fees become
   orphans and analysis JOINs silently drop them. Fix: add
   `REFERENCES crawl_targets(id) ON DELETE SET NULL` with a backfill step.

3. **Outlier flags are mutable JSONB with no schema validation** (MED) —
   `fee_crawler/pipeline/outlier_detection.py`. Malformed or stale flags
   are unlogged. Fix: enforce a Pydantic schema at INSERT/UPDATE time and
   write an `outlier_flag_updates` audit table for mutations.

4. **Legacy `extracted_fees` reads still in TypeScript** (MED) — the
   write path is frozen
   (`20260425_freeze_extracted_fees_writes.sql`), but
   `src/lib/crawler-db/core.ts:78-96` and a handful of admin queries
   still read from it. During cutover, double-counting is possible.

5. **No human gate on auto-publish of large batches** (MED) —
   `fee_crawler/commands/publish_fees.py` will promote everything with
   `confidence ≥ 0.90` in one shot. Recommend a hard cap (e.g., abort
   `--apply` if the candidate set exceeds 10K rows without a
   `--review-token` from a spot-check run).

### Verified locally

- `python -m fee_crawler stats` connects, returns `Total institutions: 0`
  on the empty bootstrap DB — pipeline + DB layer wiring works.
- All 47 supabase migrations in the directory; 10 of 47 applied cleanly
  on a fresh DB. The rest reference tables added later by other
  migrations (out-of-order dependencies) — not a pipeline issue, just a
  bootstrap one. A proper baseline `pg_dump --schema-only` from prod
  resolves this.

## Part 3 — Codebase Audit

### Security

| Finding                                                | Where                                   | Severity |
|--------------------------------------------------------|-----------------------------------------|----------|
| `sql.unsafe(trimmed)` with regex-only writekeyword block | `src/app/admin/query/actions.ts:28`, `src/lib/admin-queries.ts` | HIGH |
| API key accepted from query string                     | `src/lib/api-auth.ts:22-24`             | MED      |
| Rate limit race between COUNT and INSERT               | `src/lib/api-rate-limit.ts:43-56`       | MED      |
| CSP allows `'unsafe-inline'` for scripts and styles    | `next.config.ts:32`                     | MED      |
| Console logs include customer IDs/emails               | `src/app/api/webhooks/stripe/route.ts:22,26,48,55,100` | LOW |

**What's already solid:** HMAC session cookies with `timingSafeEqual`
verification (`src/lib/auth.ts:16-22, 35`), Stripe signature verified
before processing (`route.ts:16-23`), and SQL parameterization is the
default thanks to the `postgres` driver's tagged-template usage. No
classic injection bugs in the query layer.

### Code quality

- **`tx: any` everywhere** — 10+ instances of `sql.begin(async (tx: any) =>`.
  Should be `(tx: postgres.Sql)`. Defeats TS in transaction code.
- **60 `as unknown as` casts** in `src/lib/crawler-db/` — works, but
  obscures intent. Best-effort row mapping should be wrapped in small
  parsers (e.g., zod, or hand-rolled `parseRow` helpers).
- **Duplicate auth constants** — `SESSION_TTL_HOURS` and `SESSION_COOKIE`
  are declared in both `src/lib/auth.ts:6-7` and
  `src/app/(auth)/register/actions.ts:9`. Extract to `auth-constants.ts`.
- **Magic numbers in rate limits** —
  `src/app/submit-fees/actions.ts:6-7` hardcodes window/max; should be
  config-driven so they can be tuned without a deploy.

### Test coverage

~570 test files between TS and Python — most of the data layer and
agent flows are covered. Glaring gaps:

- `src/app/api/webhooks/stripe/route.ts` — **no tests** for idempotency,
  missing event types, or malformed payloads. This is the highest-risk
  untested route (it mutates billing state).
- `src/app/api/v1/index/route.ts` — no tests for filter combinations,
  CSV export shape, or rate-limit headers.
- `src/app/api/leads/route.ts` — no test for the permissive email regex
  edge cases.
- No server action tests (`submit-fees`, `account`, `register` actions).

### Architecture — what's working

- Strict separation of API routes / server actions / DB query layer /
  utilities. The `src/lib/crawler-db/` boundary is well-respected.
- Server components by default; client components only where they earn
  it (Cmd+K, dark mode, charts).
- Auth flow design is solid — sessions in DB, HMAC-signed cookies,
  proper flag set, expiry honored on lookup.

### Top 5 tech-debt refactors (by impact)

1. Replace `(tx: any)` with `(tx: postgres.Sql)` across all
   `sql.begin(...)` callbacks.
2. Move in-memory rate limit state to a DB-backed counter (or Redis if
   you ever add one). Currently lost on every restart.
3. Replace `sql.unsafe()` in admin query path with a real SQL parser
   (e.g., `node-sql-parser`) or restrict to a allowlist of read-only
   prepared statements.
4. Extract `SESSION_TTL_HOURS`, `SESSION_COOKIE`, HMAC algo into
   `src/lib/auth-constants.ts`. Currently duplicated.
5. Wire up structured logging — `NEXT_PUBLIC_SENTRY_DSN` is referenced
   in `CLAUDE.md` but no Sentry SDK integration is present. Stripe
   webhooks especially need trace IDs for retry debugging.
